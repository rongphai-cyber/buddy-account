## 3. สัญญาการเชื่อมต่อ "WTS Connect v1"

### 3.1 อ้างอิงต้นทาง + ส่งซ้ำไม่ลงซ้ำ (ทำใน Buddy — B0.1)

- เอกสารทุกชนิด (หัวเอกสาร และใบสำคัญ JV) มีช่อง `source_system` (เช่น `wts-pos`, `wts-living`, `wts-sop`), `source_ref` (≤ 100 ตัว), `source_version` (int)
- unique `(company_id, source_system, source_ref)` เมื่อ `deleted_at is null`
- API สร้างเอกสารรับ `source` ใน body (หรือ header `X-Source-System` / `X-Source-Ref` / `X-Source-Version` — เลือกแบบเดียวแล้วใช้ทุก endpoint):
  - ไม่มีเอกสารนี้ → สร้าง ตอบ 201 + เลขที่
  - มีแล้ว version เท่ากัน → ตอบ 200 เอกสารเดิม (ไม่สร้างซ้ำ)
  - version สูงกว่า → แก้เอกสารเดิมด้วยกลไกแก้เอกสารที่มีอยู่ (ใบสำคัญถูกแทน) · งวดปิดแล้ว → 409 `PERIOD_CLOSED` ข้อความไทยบอกให้ส่งเป็นใบปรับปรุง
  - version ต่ำกว่า → 409 `STALE_VERSION`
- เอกสารที่มี `source_system` แสดงแถบ "มาจาก WTS-POS · อ้างอิง …" · **แก้/ยกเลิกที่หน้าจอ Buddy ไม่ได้** (ต้องทำที่ต้นทาง) ยกเว้นผู้ใช้ระดับอนุมัติ 9 ยกเลิกได้พร้อมเหตุผล (บันทึก log)
- ทดสอบ: ส่งซ้ำ 2 ครั้งได้เอกสารเดียว · ข้ามบริษัทไม่ได้ · ใช้ได้ทั้ง PostgreSQL และ PGlite · เครื่องสาขาออฟไลน์ของ Buddy ไม่กระทบ

### 3.2 รูปแบบเรียก

- กุญแจ API ต่อบริษัท ผูกผู้ใช้ระบบเฉพาะ (เช่น ผู้ใช้ `SYS-POS`) ให้สิทธิ์เท่าที่ใช้
- เงินเป็นข้อความทศนิยม · วันที่ `YYYY-MM-DD` ค.ศ. · ผิดพลาดตามรูปแบบ `{ error: { code, message, issues } }` ของ Buddy
- ยอดต้องตรงต้นทางทุกสตางค์: ส่ง `vat_amount` และยอดรวมที่ต้นทางคำนวณไปด้วย · Buddy คำนวณเองแล้วเทียบ ถ้าต่าง → 422 `AMOUNT_MISMATCH` (ไม่บันทึก) · ห้ามปัดให้ตรงเงียบ ๆ

### 3.3 ฟีดข้อมูลหลักที่เปลี่ยน (Buddy — B0.2)

- `GET /api/v1/changes?since=<cursor>&types=item,customer,supplier,branch,warehouse,payment_method,doc_type,unit` ต่อยอดจาก `sync_change_log`
- ตอบเฉพาะช่องที่โปรแกรมอื่นต้องใช้ + แถวที่ถูกลบ/เลิกใช้ + `next_cursor`
- โปรแกรมอื่นเก็บสำเนาใน `ref_*` (อ่านอย่างเดียว) และดึงทุก 1–5 นาที + ปุ่ม "ดึงข้อมูลใหม่"

### 3.4 Connector (ทุกโปรแกรม — `packages/connector`)

- ตาราง `outbox(id, company_ref, kind, source_ref, version, payload jsonb, status, buddy_doc_no, error_code, error_message, tries, next_try_at, created_at, sent_at)` เขียนในทรานแซกชันเดียวกับงานต้นทาง
- ตัวส่ง: ส่งตามลำดับต่อบริษัท · ล้มเหลวชั่วคราว (เน็ต/5xx/429) ลองใหม่แบบเว้นระยะ · ล้มเหลวถาวร (4xx) หยุดคิวบริษัทนั้น แสดงหน้า "ส่งเข้าบัญชี" ให้แก้แล้ว "ส่งใหม่"
- ปลายทางเลือกได้ต่อบริษัท: `buddy` / `file` (CSV/Excel ใบสำคัญรายวัน) / `none`
- สถานะรวมส่งให้ `SyncStatus` (รอส่ง n / ไม่ผ่าน n)

### 3.5 ทำงานต่อได้เมื่อเน็ตหลุด / ระบบบัญชีล่ม (D11 · เจ้าของ 05/11/2569 — ใช้กับทุกโปรแกรมหน้างาน)

แยกข้อมูลเป็น 2 ชั้น แต่ละชั้นล่มได้โดยไม่หยุดงานหน้าร้าน:

| ชั้น | ขาดอะไร | ต้องทำได้ | วิธี |
|---|---|---|---|
| **เครื่องหน้างาน** (จอแคชเชียร์ เคาน์เตอร์สปา หน้าฟรอนต์โรงแรม แท็บเล็ต) ↔ เซิร์ฟเวอร์ของโปรแกรม | อินเทอร์เน็ตที่ร้าน | เปิดโปรแกรม ขาย/เช็คอิน รับเงิน พิมพ์ใบเสร็จ/ใบกำกับอย่างย่อ ปิดกะ ได้ครบ | ตัวโปรแกรมเก็บในเครื่อง (PWA service worker) · สำเนาข้อมูลหลัก (สินค้า ราคา โปร ห้อง พนักงาน) ในเครื่อง · บันทึกลงเครื่องก่อน (เก็บถาวร ปิดเบราว์เซอร์/ไฟดับไม่หาย — ข้อมูลมากใช้ IndexedDB) · คิวรอส่งในเครื่อง ส่งเองเมื่อเน็ตกลับ ตามลำดับ |
| **เซิร์ฟเวอร์ของโปรแกรม** ↔ Buddy | Buddy ล่ม/ปิดปรับปรุง/เน็ตระหว่างเซิร์ฟเวอร์ | ทุกอย่างของโปรแกรมทำงานปกติ · Buddy ไม่ใช่ขั้นตอนที่ต้องรอตอนขาย | outbox (ข้อ 3.4) เขียนในทรานแซกชันเดียวกับงาน · ล้มเหลวชั่วคราวลองใหม่แบบเว้นระยะไม่จำกัดวัน · Buddy กลับมา = ส่งย้อนหลังตามลำดับเอง · ข้อมูลหลักใช้สำเนา `ref_*` ล่าสุด แล้วต่อฟีดจาก cursor เดิม |

กติกา (ทุกโปรแกรมต้องผ่าน):
1. **ส่งซ้ำไม่ลงซ้ำ** — ทุกงานที่ค้างมีรหัสของตัวเองตั้งแต่ในเครื่อง (UUID) · ส่งเข้าเซิร์ฟเวอร์ซ้ำได้ผลเดิม · ส่งเข้า Buddy ด้วย `X-Source-Ref` เดิม (ข้อ 3.1)
2. **เลขที่เอกสารไม่ชนกันตอนออฟไลน์** — เลขที่ออกในเครื่องมีรหัสเครื่อง/จุดขายนำหน้า (เช่น ใบกำกับอย่างย่อแยกชุดต่อเครื่องตามที่ยื่นกรมสรรพากร) · ไม่ต้องรอเซิร์ฟเวอร์ออกเลข
3. **ยอดเงินคำนวณในเครื่องด้วยตรรกะชุดเดียวกับเซิร์ฟเวอร์** (`packages/shared`) — ส่งขึ้นแล้วยอดต้องตรงทุกสตางค์ (`source_totals`) ต่างเมื่อไหร่ = หยุดแจ้ง ห้ามปรับตัวเลข
4. **เห็นสถานะเสมอ** — ป้าย ออนไลน์ / ออฟไลน์ / รอส่ง n / ส่งไม่ผ่าน n ที่หน้าจอ · ส่งไม่ผ่านถาวร (เช่น Buddy ไม่รับ) ค้างไว้พร้อมข้อความไทยและปุ่มส่งใหม่ ห้ามทิ้ง
5. **เรื่องที่เกิดระหว่างออฟไลน์** — สต๊อกติดลบได้ (เตือน ตรวจทีหลัง) · ราคา/โปรที่เปลี่ยนระหว่างนั้นมีผลเมื่อเครื่องได้ข้อมูลใหม่ · งานที่ต้องตรวจสิทธิ์ออนไลน์ (เช่น วงเงินลูกหนี้ แต้มสมาชิกข้ามสาขา) ทำแบบมีเงื่อนไขแล้วตรวจซ้ำตอนส่ง · เวลาใช้เวลาเครื่อง (Asia/Bangkok)
6. **ทดสอบรับมอบทุกโปรแกรม (ต้องมีชุดทดสอบอัตโนมัติ)**:
   - ตัดเน็ต → ขาย/เช็คอินหลายรายการ → ปิดแล้วเปิดเบราว์เซอร์ใหม่ (ข้อมูลยังอยู่) → ต่อเน็ต → ส่งครบครั้งเดียว ยอดตรง
   - Buddy ล่มทั้งวัน → หน้าร้านใช้ได้ปกติ → Buddy กลับมา → เอกสารเข้า Buddy ครบครั้งเดียว งบทดลองตรงกับตัวเลขคำนวณไว้
   - ส่งซ้ำ/เน็ตหลุดกลางการส่ง → ไม่มีเอกสารซ้ำ
7. Buddy เอง: สาขาที่เน็ตไม่เสถียรใช้เครื่องสาขาออฟไลน์ตาม `docs/12_ออฟไลน์สาขา.md` (T7.8 — รอเจ้าของจัดลำดับ)

### 7.3 ค่าธรรมเนียมแฟรนไชส์
ยอดขาย 280,000 ก่อน VAT · ค่าสิทธิ์ 5% = 14,000 · การตลาด 2% = 5,600 (รวม 19,600 > ขั้นต่ำ 10,000) · ค่าระบบ 1,500 → 21,100 + VAT 1,477 = **22,577**

## 8. ความเสี่ยงที่ต้องเฝ้า

- **ยอดไม่ตรงเพราะปัดเศษต่างกัน** ระหว่าง POS (คิดรายบิล) กับ Buddy (คิดรายเอกสาร) → ข้อ 3.2 บังคับเทียบ
- **ข้อมูลหลักไม่ทัน** (สินค้าใหม่ใน POS ยังไม่มีใน Buddy) → Buddy ตอบ 422 ระบุรหัส · POS แสดงในหน้า "ส่งเข้าบัญชี" ให้ผูกรหัสแล้วส่งใหม่
- **งวดปิดแล้ว** → ส่งเป็นใบปรับปรุง ไม่แก้ย้อนหลัง
- **กุญแจ API รั่ว** → ผู้ใช้ระบบสิทธิ์น้อยที่สุด · ยกเลิกได้ทันที · กุญแจแฟรนไชส์เก็บเข้ารหัส
- **รุ่น API** → ทุกโปรแกรมส่ง header รุ่น Connector · Buddy เปลี่ยนสัญญาต้องเป็น `/api/v2` หรือคงของเดิม

## 9. คำถามที่ยังเปิด (ถามเจ้าของเมื่อถึงงาน)

1. รูปแบบรายงานภาษีขายสำหรับใบกำกับอย่างย่อ (B0.4) — ให้สำนักงานบัญชียืนยันกับประกาศที่ใช้บังคับ
2. ร้านแพ็กเกจ POS อย่างเดียวต้องการ "อัปเกรดเป็น Buddy" แล้วส่งยอดย้อนหลังตั้งแต่วันไหน
3. Hotel/Spa จะยกออกจาก WTS-ERP เมื่อไร (B7)
4. WTS-SOP จะรับ token จาก Buddy หรือคงล็อกอินแยก (B6.3)
