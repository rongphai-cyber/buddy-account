# หลายลูกค้า (Multi-tenant) และความปลอดภัยของข้อมูล

หลักการ: Buddy Account ขายหรือให้บริการแก่ลูกค้าหลายรายบนระบบเดียวได้ โดย **ข้อมูลของลูกค้าแต่ละรายไม่ปนกันและมองไม่เห็นกัน**

## 1. ลำดับชั้นข้อมูล

```
ผู้ให้บริการโปรแกรม (platform)            ← เจ้าหน้าที่ Buddy: ผู้ใช้กลุ่ม ADMIN ที่ไม่สังกัดลูกค้า
 └── ลูกค้าผู้ใช้บริการ  sys_tenant          ← สำนักงานบัญชี / บริษัทที่ซื้อโปรแกรม
      ├── ผู้ใช้        sys_user.tenant_id
      ├── กลุ่มผู้ใช้    sys_user_group.tenant_id  (รหัสกลุ่มซ้ำกันข้ามลูกค้าได้ เช่น ADMIN ของแต่ละราย)
      └── บริษัท        sys_company.tenant_id (บังคับ)
           └── ข้อมูลทุกตาราง company_id
```

| ผู้ใช้ | เห็นอะไร |
|---|---|
| เจ้าหน้าที่ผู้ให้บริการ (ADMIN ไม่มี tenant) | ทุกลูกค้า ทุกบริษัท; หน้า "ลูกค้าผู้ใช้บริการ" |
| ผู้ดูแลระบบของลูกค้า (กลุ่ม ADMIN ของลูกค้านั้น) | ทุกบริษัท/ผู้ใช้ **ของลูกค้าตัวเองเท่านั้น** |
| ผู้ใช้ทั่วไป | เฉพาะบริษัทที่ได้รับสิทธิ์ใน `sys_user_company` และต้องอยู่ในลูกค้าเดียวกัน |

## 2. สิ่งที่บังคับแล้วในรุ่นนี้

1. **บริษัทมาจาก session เท่านั้น** — `companiesForUser()` กรอง tenant ทุกครั้ง; การเลือกบริษัท/คัดลอกบริษัทตรวจว่าเข้าถึงได้ก่อน; session ที่ชี้บริษัทที่ไม่มีสิทธิ์แล้วถูกล้างอัตโนมัติ
2. **ADMIN ไม่ข้ามลูกค้า** — สิทธิ์ ADMIN นับเฉพาะกลุ่มที่อยู่ใน tenant เดียวกับผู้ใช้
3. **จัดการผู้ใช้ภายในลูกค้า** — กำหนดกลุ่ม/บริษัทให้ผู้ใช้ได้เฉพาะของลูกค้าเดียวกัน
4. **ระงับลูกค้า** — สถานะ S/I หรือเลยวันหมดอายุ: เข้าระบบไม่ได้ (403 `TENANT_SUSPENDED`) และ session ที่ค้างอยู่ถูกตัดทันที
5. **โควตาแพ็กเกจ** — `max_companies`, `max_users`
6. **บันทึกการใช้งาน** — ผู้ดูแลของลูกค้าเห็น log เฉพาะบริษัทของตน; log แก้/ลบไม่ได้
7. **รหัสผ่าน** bcrypt, cookie httpOnly + SameSite, เก็บ session เป็น sha256 (ขโมยฐานข้อมูลไปก็ใช้ session ไม่ได้)
8. **ชุดทดสอบ** `separates customer tenants completely` — ลูกค้า A มองไม่เห็นบริษัท ผู้ใช้ ใบสำคัญ และ log ของลูกค้า B, ADMIN ของ A เลือกบริษัทของ B ไม่ได้
9. **สิทธิ์ 7 ชนิดรายเมนู (T0.10)** — ระดับอนุมัติ + ตารางสิทธิ์ Y/L/N/S บังคับที่ API ทุกเส้นใน `apps/server/src/modules/permissions.ts` (`API_RULES`); API ที่ไม่มีกฎถูกปฏิเสธ และชุดทดสอบตรวจว่าครบทุกเส้น
10. **Row-Level Security (T0.14) — ป้องกันชั้นที่สองในฐานข้อมูล**
    - API ข้อมูลบริษัท (กฎ menu/lookup) ทำงานทั้งคำขอในทรานแซกชันเดียว: `SET LOCAL ROLE buddy_app` + `set_config('app.company_id' / 'app.tenant_id' / 'app.platform', …, true)` (`runInCompanyScope` ใน `apps/server/src/db.ts`)
    - `buddy_app` ไม่ใช่เจ้าของตาราง จึงอยู่ใต้นโยบาย: ทุกตารางที่มี `company_id` เห็น/เขียนได้เฉพาะบริษัทของคำขอ (ไม่ได้ตั้งค่า = ไม่เห็นอะไรเลย); `sys_company`/`sys_tenant`/`sys_user`/`sys_user_group`/`sys_user_company` จำกัดตามลูกค้า; `sys_activity_log` = บริษัทนี้หรือเหตุการณ์ระดับระบบ
    - เจ้าของฐานข้อมูล (migration, นำเข้าข้อมูล Express, เข้าระบบ, จัดการผู้ใช้/ลูกค้า/สร้างบริษัท) ไม่ถูกจำกัด — ส่วนนี้ตรวจในโค้ด
    - โค้ดใช้ `database.db` เสมอ (ส่งต่อเข้าทรานแซกชันของคำขอให้อัตโนมัติ); `database.raw` ใช้เปิดทรานแซกชันเท่านั้น — บน PGlite ถ้าใช้ raw ภายในคำขอจะค้าง
    - โฮสต์ที่สร้าง role ไม่ได้: migration ข้ามส่วน role และ server แจ้งเตือนแล้วทำงานแบบกรองในโค้ดอย่างเดียว
    - **ตารางใหม่ที่มี `company_id` ต้องเปิด RLS + นโยบาย `buddy_company` ใน migration ของตัวเอง** — ชุดทดสอบตรวจว่าทุกตารางเปิดแล้ว

## 3. งานเสริมความปลอดภัยถัดไป (TASKS T0.14–T0.18)

| งาน | รายละเอียด |
|---|---|
| ~~T0.14 Row-Level Security~~ | เสร็จแล้ว (ดูข้อ 10 ด้านบน) |
| T0.15 สำรอง/ส่งออกข้อมูลรายลูกค้า | ลูกค้าดาวน์โหลดข้อมูลของตัวเองได้, กู้คืนรายลูกค้าโดยไม่กระทบรายอื่น |
| T0.16 ยืนยันตัวตนสองขั้น + ล็อกการเข้าระบบ | TOTP, ล็อกหลังผิดรหัส n ครั้ง, นโยบายรหัสผ่าน |
| T0.17 PDPA | ทะเบียนข้อมูลส่วนบุคคล, การลบ/ปิดบังข้อมูลเมื่อเลิกใช้บริการ, ข้อตกลงการประมวลผลข้อมูล |
| T0.18 ฐานข้อมูลแยกต่อลูกค้า (ทางเลือก) | ลูกค้ารายใหญ่ขอฐานข้อมูล/เซิร์ฟเวอร์แยก — โค้ดเดิมใช้ได้เพราะ tenant เป็นแค่ตัวกรอง |

## 4. กติกาเขียนโค้ด (อยู่ใน CLAUDE.md)

- ทุก query กรอง `company_id` จาก session; query ระดับผู้ใช้/กลุ่ม/บริษัทกรอง `tenant_id` จาก session
- ห้ามเชื่อ `tenant_id`/`company_id` ที่ส่งมาจากหน้าจอ — ยกเว้นเจ้าหน้าที่ผู้ให้บริการ และต้องตรวจสิทธิ์ก่อน
- API ใหม่ที่อ่านข้อมูลข้ามบริษัทต้องมีชุดทดสอบว่าข้ามลูกค้าไม่ได้

## 5. ข้อมูลตัวอย่าง

`tools/demo-data/make_demo.py` แปลงข้อมูล TESTRice จาก Express เป็นบริษัทสมมุติ **DEMO** ในลูกค้า **DEMO**
- เลื่อนวันที่ +16 ปี (2552–2553 → 2568–2569), แก้วันที่ผิด, ลบปีบัญชีที่เกิดจากพิมพ์ผิด
- ชื่อลูกค้า/ผู้จำหน่าย/บริษัทเป็นชื่อสมมุติ, เลขผู้เสียภาษี 13 หลักสมมุติที่หลักตรวจสอบถูกต้อง (ขึ้นต้น 0000 นิติบุคคล / 1000 บุคคล), ปิดเลขบัญชีธนาคาร
- ยอดเดบิต/เครดิตรายปีเท่าเดิมทุกบาท
