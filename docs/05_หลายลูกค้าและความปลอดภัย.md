# หลายลูกค้า (Multi-tenant) และความปลอดภัยของข้อมูล

หลักการ: Buddy Account ขายหรือให้บริการแก่ลูกค้าหลายรายบนระบบเดียวได้ โดย **ข้อมูลของลูกค้าแต่ละรายไม่ปนกันและมองไม่เห็นกัน**

## 1. ลำดับชั้นข้อมูล

```
ผู้ให้บริการโปรแกรม (platform)            ← เจ้าหน้าที่ Buddy: ผู้ใช้กลุ่ม ADMIN ที่ไม่สังกัดลูกค้า
 └── ลูกค้าผู้ใช้บริการ  sys_tenant          ← สำนักงานบัญชี / บริษัทที่ซื้อโปรแกรม
      ├── ผู้ใช้        sys_user.tenant_id
      ├── กลุ่มผู้ใช้    sys_user_group.tenant_id  (รหัสกลุ่มซ้ำกันข้ามลูกค้าได้ เช่น ADMIN ของแต่ละราย)
      └── บริษัท        sys_company.tenant_id (บังคับ)
           └── ข้อมูลทุกตาราง company_id
```

| ผู้ใช้ | เห็นอะไร |
|---|---|
| เจ้าหน้าที่ผู้ให้บริการ (ADMIN ไม่มี tenant) | ทุกลูกค้า ทุกบริษัท; หน้า "ลูกค้าผู้ใช้บริการ" |
| ผู้ดูแลระบบของลูกค้า (กลุ่ม ADMIN ของลูกค้านั้น) | ทุกบริษัท/ผู้ใช้ **ของลูกค้าตัวเองเท่านั้น** |
| ผู้ใช้ทั่วไป | เฉพาะบริษัทที่ได้รับสิทธิ์ใน `sys_user_company` และต้องอยู่ในลูกค้าเดียวกัน |

## 2. สิ่งที่บังคับแล้วในรุ่นนี้

1. **บริษัทมาจาก session เท่านั้น** — `companiesForUser()` กรอง tenant ทุกครั้ง; การเลือกบริษัท/คัดลอกบริษัทตรวจว่าเข้าถึงได้ก่อน; session ที่ชี้บริษัทที่ไม่มีสิทธิ์แล้วถูกล้างอัตโนมัติ
2. **ADMIN ไม่ข้ามลูกค้า** — สิทธิ์ ADMIN นับเฉพาะกลุ่มที่อยู่ใน tenant เดียวกับผู้ใช้
3. **จัดการผู้ใช้ภายในลูกค้า** — กำหนดกลุ่ม/บริษัทให้ผู้ใช้ได้เฉพาะของลูกค้าเดียวกัน
4. **ระงับลูกค้า** — สถานะ S/I หรือเลยวันหมดอายุ: เข้าระบบไม่ได้ (403 `TENANT_SUSPENDED`) และ session ที่ค้างอยู่ถูกตัดทันที
5. **โควตาแพ็กเกจ** — `max_companies`, `max_users` · **แพ็กเกจบริการ + มาตรวัดการใช้งาน (HANDOFF 185 · แบบ A เอกสาร+ไฟล์)**: ตาราง `sys_package` (ผู้ให้บริการแก้/เพิ่ม · ตั้งต้น 4 แพ็กเกจ migration 0076) · `sys_tenant.package_id` + ค่าทับรายลูกค้า (ว่าง = ตามแพ็กเกจ · ไม่มีแพ็กเกจ = ไม่จำกัด) · ยอดใช้งานคำนวณสดทุกครั้ง (`apps/server/src/modules/usage.ts` · คณิตส่วนเกินใน `packages/core/src/usage.ts`) · เอกสารไม่หยุดเด็ดขาด · ไฟล์/AI ครบ 100% + ลูกค้าตั้ง "หยุด" = ปฏิเสธก่อนเปิดทรานแซกชันของบริษัท (preHandler) · ลูกค้าเห็นเฉพาะของตัวเอง (`GET /api/v1/usage` ผู้ดูแลของลูกค้า) · แค็ตตาล็อก/ทุกลูกค้า/ส่วนเกิน = ผู้ให้บริการเท่านั้น
6. **บันทึกการใช้งาน** — ผู้ดูแลของลูกค้าเห็น log เฉพาะบริษัทของตน; log แก้/ลบไม่ได้
7. **รหัสผ่าน** bcrypt, cookie httpOnly + SameSite, เก็บ session เป็น sha256 (ขโมยฐานข้อมูลไปก็ใช้ session ไม่ได้)
8. **ชุดทดสอบ** `separates customer tenants completely` — ลูกค้า A มองไม่เห็นบริษัท ผู้ใช้ ใบสำคัญ และ log ของลูกค้า B, ADMIN ของ A เลือกบริษัทของ B ไม่ได้
9. **สิทธิ์ 7 ชนิดรายเมนู (T0.10)** — ระดับอนุมัติ + ตารางสิทธิ์ Y/L/N/S บังคับที่ API ทุกเส้นใน `apps/server/src/modules/permissions.ts` (`API_RULES`); API ที่ไม่มีกฎถูกปฏิเสธ และชุดทดสอบตรวจว่าครบทุกเส้น
10. **Row-Level Security (T0.14) — ป้องกันชั้นที่สองในฐานข้อมูล**
    - API ข้อมูลบริษัท (กฎ menu/lookup) ทำงานทั้งคำขอในทรานแซกชันเดียว: `SET LOCAL ROLE buddy_app` + `set_config('app.company_id' / 'app.tenant_id' / 'app.platform', …, true)` (`runInCompanyScope` ใน `apps/server/src/db.ts`)
    - `buddy_app` ไม่ใช่เจ้าของตาราง จึงอยู่ใต้นโยบาย: ทุกตารางที่มี `company_id` เห็น/เขียนได้เฉพาะบริษัทของคำขอ (ไม่ได้ตั้งค่า = ไม่เห็นอะไรเลย); `sys_company`/`sys_tenant`/`sys_user`/`sys_user_group`/`sys_user_company` จำกัดตามลูกค้า; `sys_activity_log` = บริษัทนี้หรือเหตุการณ์ระดับระบบ
    - เจ้าของฐานข้อมูล (migration, นำเข้าข้อมูล Express, เข้าระบบ, จัดการผู้ใช้/ลูกค้า/สร้างบริษัท) ไม่ถูกจำกัด — ส่วนนี้ตรวจในโค้ด
    - โค้ดใช้ `database.db` เสมอ (ส่งต่อเข้าทรานแซกชันของคำขอให้อัตโนมัติ); `database.raw` ใช้เปิดทรานแซกชันเท่านั้น — บน PGlite ถ้าใช้ raw ภายในคำขอจะค้าง
    - โฮสต์ที่สร้าง role ไม่ได้: migration ข้ามส่วน role และ server แจ้งเตือนแล้วทำงานแบบกรองในโค้ดอย่างเดียว
    - **ตารางใหม่ที่มี `company_id` ต้องเปิด RLS + นโยบาย `buddy_company` ใน migration ของตัวเอง** — ชุดทดสอบตรวจว่าทุกตารางเปิดแล้ว

11. **สมัครใช้งานเอง (ข้อกำหนดเจ้าของ 30/10/2569)** — `POST /api/v1/signup` ไม่ต้องเข้าระบบ แต่ไม่สร้างอะไรในข้อมูลลูกค้าเดิม: เก็บใบสมัครใน `sys_signup` (ไม่มี company_id) · `BUDDY_SIGNUP=review` (ค่าเริ่มต้น) เจ้าหน้าที่ผู้ให้บริการอนุมัติก่อน = สร้าง tenant ใหม่ + กลุ่ม ADMIN + ผู้ดูแลคนแรก (ไม่มีทางผูกกับ tenant/บริษัทเดิม) · `auto` อนุมัติทันที · `off` ปิด · กันสแปม: ช่องดักบอท, 5 ใบ/IP/ชั่วโมง, รออนุมัติรวมไม่เกิน 500, รหัสผู้ใช้/อีเมลซ้ำไม่ได้ · รหัสผ่าน bcrypt ล้างทิ้งเมื่อพิจารณาแล้ว · ใบที่ไม่อนุมัติล้างข้อมูลติดต่อเมื่อครบ 90 วัน (PDPA) · อนุมัติแล้วสร้างบริษัทแรกในลูกค้ารายใหม่นั้นเท่านั้น (HANDOFF 154) · **ผู้ใช้ดูอย่างเดียว** `POST /api/v1/tenants/:id/viewers` (เจ้าหน้าที่ผู้ให้บริการเท่านั้น): ผู้ใช้อยู่ใน tenant ที่ให้ดู (เช่น DEMO) กลุ่ม VIEW อ่าน/พิมพ์ออกจอ ที่เหลือไม่ได้ — ไม่ใช่สิทธิ์ข้าม tenant · ทดสอบใน api.test (ผู้ใช้ดูอย่างเดียวเลือกบริษัทของลูกค้ารายอื่นไม่ได้ เขียนไม่ได้)

12. **สำรอง/นำข้อมูลกลับรายบริษัทและข้อมูลผู้ใช้ (HANDOFF 146 · เจ้าของ 19/11/2569 "ทำทั้ง 4 ข้อ")** — `apps/server/src/modules/backup.ts`
    - **เข้ารหัสทั้งแฟ้ม** ด้วยรหัสผ่านที่ผู้ใช้ตั้งตอนสำรอง (≥ 8 ตัว ป้อน 2 ครั้ง) · AES-256-GCM กุญแจจาก scrypt(รหัสผ่าน + salt) · หัวแฟ้มมีค่าตรวจรหัสผ่าน จึงบอกได้ชัดว่า "รหัสผิด" หรือ "แฟ้มเสีย" · ผู้ให้บริการกู้รหัสให้ไม่ได้
    - รหัสผ่านส่งใน body (สำรอง) / หัวคำขอ `x-backup-password` (ทดสอบ/นำกลับ) ไม่อยู่ใน URL ไม่ลง log · บันทึกเหตุการณ์ BACKUP/RESTORE/BACKUP_USERS/RESTORE_USERS เก็บผู้ใช้ ชื่อแฟ้ม จำนวนแถว รุ่นโครงสร้าง — ไม่มีรหัสผ่าน
    - แฟ้มรุ่นก่อน (gzip ไม่เข้ารหัส) ยังทดสอบ/นำกลับได้ หน้าจอเตือนให้สำรองใหม่
    - **นำกลับข้ามรุ่นโปรแกรม**: แฟ้มจากรุ่นโครงสร้างข้อมูลเก่ากว่า → แทรกตามชื่อช่อง (ช่องที่เพิ่มภายหลังได้ค่าเริ่มต้น · ตารางใหม่ว่าง) แล้วทำขั้นปรับข้อมูลของ migration ที่แปลงข้อมูลเดิม (`COMPANY_STEPS` 0038 0039 0050 0053 0055 0056 · `USER_STEPS` 0060 0068 — ชุดทดสอบตรวจว่า migration ที่แก้ข้อมูลบริษัท/ผู้ใช้ตั้งแต่ 0023 อยู่ในรายการ) แล้วเติมกฎการลงบัญชีที่เพิ่มในรุ่นหลัง · แฟ้มรุ่นใหม่กว่า = "อัปเดตโปรแกรมก่อน" · ช่อง/ตารางที่ระบบไม่มีแล้ว = ปฏิเสธ (ไม่เดา)
    - **ตรวจหลังนำกลับในทรานแซกชันเดียวกัน**: จำนวนแถวทุกตาราง + จำนวนใบสำคัญ/ผลรวมเดบิต/เครดิต (แฟ้มใหม่มียอดในหัวแฟ้ม) ไม่ตรง = ยกเลิกทั้งหมด ข้อมูลเดิมไม่หาย · หน้าจอแสดงผลการตรวจ · สำรองอ่านทุกตารางใน snapshot เดียว (repeatable read)
    - **สิทธิ์**: ดาวน์โหลดแฟ้มทั้งบริษัท/นำกลับ (OT.BACKUP เพิ่ม/แก้ไข) = ผู้ดูแลระบบหรือระดับ 9 — ระดับ 5–8 ต้องได้รับสิทธิ์ที่เมนูนี้โดยตรง (แถวสิทธิ์ผู้ใช้/กลุ่มที่ OT.BACKUP) แม้ไม่ได้ตรวจสิทธิ์ก่อนใช้งาน · ทดสอบแฟ้ม (อ่าน) ยังทำได้ · ข้อมูลผู้ใช้ = ผู้ดูแลของลูกค้าเท่านั้น (เดิม) · **ลูกค้าเดิมไม่เสียสิทธิ์**: migration 0068 สร้างแถวสิทธิ์ให้ผู้ใช้ระดับ 5–8 ที่เคยสำรองได้ (ผลทุกการทำงานเท่าเดิม) — ผู้ใช้ใหม่หลังอัปเกรดผู้ดูแลต้องให้สิทธิ์เอง
13. **ลูกค้าบังคับยืนยันตัวตนสองขั้นทุกผู้ใช้ (HANDOFF 146)** — `sys_tenant.require_mfa` (migration 0069 · ค่าเริ่มต้น ปิด) ตั้งที่ **ระดับลูกค้า** เพราะผู้ใช้หนึ่งคนเข้าได้หลายบริษัทของลูกค้าเดียวกัน (ถ้าตั้งรายบริษัท ผู้ใช้คนเดียวจะถูกบังคับบ้างไม่บังคับบ้างตามบริษัทที่เลือก) · ผู้ดูแลระบบของลูกค้าตั้งที่หน้า ผู้ใช้งานระบบ (`GET/PUT /api/v1/tenant/security`) · เปิดแล้ว ผู้ใช้ที่ยังไม่ตั้งได้ `mfa_setup_required` ทุกคำขอ (session ที่เปิดอยู่ถูกบังคับตั้งแต่คำขอถัดไป) ใช้ได้เฉพาะหน้าตั้งค่า · เจ้าหน้าที่ผู้ให้บริการ (ไม่มี tenant) และลูกค้ารายอื่นไม่กระทบ (ชุดทดสอบตรวจ) · ผู้ดูแลระบบบังคับเสมอเหมือนเดิม

- ทุก query กรอง `company_id` จาก session; query ระดับผู้ใช้/กลุ่ม/บริษัทกรอง `tenant_id` จาก session
- ห้ามเชื่อ `tenant_id`/`company_id` ที่ส่งมาจากหน้าจอ — ยกเว้นเจ้าหน้าที่ผู้ให้บริการ และต้องตรวจสิทธิ์ก่อน
- API ใหม่ที่อ่านข้อมูลข้ามบริษัทต้องมีชุดทดสอบว่าข้ามลูกค้าไม่ได้

## 5. ข้อมูลตัวอย่าง

`tools/demo-data/make_demo.py` แปลงข้อมูล TESTRice จาก Express เป็นบริษัทสมมุติ **DEMO** ในลูกค้า **DEMO**
- เลื่อนวันที่ +16 ปี (2552–2553 → 2568–2569), แก้วันที่ผิด, ลบปีบัญชีที่เกิดจากพิมพ์ผิด
- ชื่อลูกค้า/ผู้จำหน่าย/บริษัทเป็นชื่อสมมุติ, เลขผู้เสียภาษี 13 หลักสมมุติที่หลักตรวจสอบถูกต้อง (ขึ้นต้น 0000 นิติบุคคล / 1000 บุคคล), ปิดเลขบัญชีธนาคาร
- ยอดเดบิต/เครดิตรายปีเท่าเดิมทุกบาท
